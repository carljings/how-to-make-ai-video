# 2026-10-22 制作记录

用户反馈：动效不够惊艳、讲解不够精彩、BGM没有。

确认第一版有音乐文件，但对白时全段衰减到32%，配器偏低频。正确的处理是重新编排和混音，不以“文件里有轨道”反驳观看体验。独立建立第二版目录，未覆盖旧片。

先写修订目标与完整新旁白。18段 Edge TTS 生成中有一次 NoAudioReceived，下一次运行复用已成功片段并补齐；没有换账户、启用付费语音或修改代理配置。字体一次 urllib TLS EOF 后，按 tunnel-doctor 的分层原则仅更换本次下载的客户端为 curl 完成原字体资源读取；没有调整全局网络。

第一轮新画面检查发现：方法完整序列在短镜头里过快、状态分组卡重叠模糊、结尾网址与物体太近。随后把方法改为明确标注的阶段节选，保留完整算法并逐目标验算；分组卡退去重叠层，网址与最后姿态拉开。

后续动态检查又发现 F2L 参考高亮仍是另一组、机位看不到最后一组。改为实际示例的 C6/E11（白红蓝角与蓝红棱），从左后槽观看最后六个实际动作。字幕和标题让出物体的最高位置。超级翻转最后的缩小魔方也避开“上帝之数”文字。

音乐先按整片归一，测量发现后半段偏强。改为按旁白段落平衡：方法段约-8dB，普通段约-9dB，较细解释段约-10.5dB；这些是分段声轨均方电平目标，不等于每个瞬时采样的听感。最后的实际编码响度另行测量。

最初的音乐反解检查错误混用了原始单声道与 FFmpeg 默认立体声转单声道，导致音乐系数被系统性低估约3dB。检查方式改为原始单声道人声、立体声算术均值，与实际混音一致。动态响度处理使部分短窗口不适合线性拟合，因此检查各段的中位增益比和有足够解释能量的窗口，保留全部拟合结果，不把所有窗口写成通过。

最终以编码 MP4 的画面、AAC、人声/音乐/效果声轨、实际解法状态和字幕时间轴分别检查。技术通过与用户是否认可审美分开。未进行主观听审、实体手机审看或外部发布。

收尾动态检查发现问句在魔方缩小时短暂压住顶面，改为在物体落定与终止和弦之后出现；20步段的文字也让开主体。一次封装在这轮渲染结束前提前启动，发现读到前一版画面后不采用该结果；待渲染明确结束后重新封装。最终增加原渲染与交付 MP4 的 H.264 包哈希一致检查，并确认检查期间原渲染文件没有变化，避免把旧画面装进新版交付。
