# Opus 代码视频制作方法：导演思路、动效与原版渲染链路

[English](../opus-video-production-method.md) · 核对日期：2026-10-24

本文来自一次实际 Claude Code／Opus 魔方科普片的核对：简报、分镜、场景源码、制作记录和编码后抽帧。
用户已选择该原版作为审美基准。这里记录的是一个已观察的工作流，不把它推成所有 Opus 视频的唯一技术栈，也不把型号当作质量保证。

可复用的方法是：为每个概念设计可见动作，用统一时间轴协调画面与声音，修订时保留已经选定的视觉语言。

## 1. 先决定怎么讲，再写实现

先明确观众的问题，以及结尾必须交付的答案；中间收束到少数相互连接的概念。
魔方片用三个数字串起解释，最后用真实成绩卡回到开头的比赛疑问；计时器归零让结尾问句有了具体动作。

写场景前先有简报、事实表、分镜和风格测试。每个镜头写清：

- 观众看完应理解什么；
- 用哪个主要动作把它表现出来；
- 构图、运镜、强调对象，以及贴近动作的短文字；
- 音乐或音效落点，以及镜头结束时留下的状态。

按用户已经确认的分镜推进，已有明确授权的例行步骤不重复询问。事实、单位和轮次／评分语境约束文案；一句话再有冲击力，也不能暗示错误因果。

## 2. 让动效承担解释

| 要讲的内容 | 本例采用的动作 | 必须保持清楚的关系 |
|---|---|---|
| 内部结构 | 线框、轴心、转轴和爆炸拆解 | 拆开前后仍是同一对象 |
| 排列 | 角块、棱块换位 | 对象身份与屏幕位置分开追踪 |
| 朝向约束 | 零件扭转／翻面，标记最后一个受约束的块 | 标记跟随正确零件的当前姿态 |
| 数学界限 | 上界和下界在 20 处合拢 | 动画解释证明，不冒充证明本身 |
| 人的解法 | 真实转层，到达不同阶段目标 | 高亮、文字和实际状态一致 |
| 五次平均 | 五张卡入场，两张移出，三张合并 | 数据和比赛轮次明确 |
| 收尾 | 回到开头的魔方，计时器归零，声音衰减 | 文件结束前完成首问的回扣 |

按解释需要使用近景、环绕、拉远、拆解、图表和卡片；跨镜头保持对象身份、颜色含义和因果连续。
避免每个概念重复同一套“标题／居中魔方／底部字幕”，也避免无关运动与阅读抢注意力。

节奏要服从用途。短片概述不需要逐步教授每一个公式动作。逐阶段加停顿或固定机位，可能更方便逐帧检查，却削弱用户喜欢的连续动势。
应判断整段的效果，不能只凭静态图或“每秒多少步”决定必须放慢。

## 3. 原版实际怎样渲染

原版采用 Canvas 2D、自写魔方模型和透视绘制。Node 编排 headless Chrome，真正绘图发生在浏览器中，不是由 Node 原生 Canvas 替代导出。

1. 预先计算带种子的视觉数据和真实动作状态快照。
2. 用影片时间决定每一帧，例如“帧号 ÷ 帧率”；不依赖系统时钟、未固定的随机数或先前渲染的顺序。
3. 加载本地字体，等待影片就绪。
4. 在 Chrome 中绘制指定时间，等待合成，截图后送入 FFmpeg。
5. 编码并拼接分块；复用分块前核对源码和时序条件。

三维观感来自透视、正确的面／转层绘制顺序、圆角面片、方向光、高光、轮廓光、接触阴影，以及多个相邻时间采样的运动模糊。
这些实现服务于镜头和解释；仅列出特效名字或要求“电影感”，不足以形成具体方案。

本地样本的模块分工如下。这里是样本工程的逻辑文件名，不是本次提交发布的源码链接：

| 模块 | 职责 |
|---|---|
| `timeline.js` | 命名事件与统一影片时钟 |
| `cube.js` | 零件身份、位置、朝向和合法动作 |
| `seqs.js` | 真实动作时序、中间快照与转动音效事件 |
| `draw3d.js` | 相机、投影、可见性、表面与时间采样 |
| `scenes/` | 每个概念的构图、动作、文字和转场 |
| `score.js` | 由同一组事件安排音乐与音效 |
| `render.mjs` | Chrome 截帧与 FFmpeg 导出 |

本例实际使用 M4 上 Chrome 的 Metal 后端，这是环境记录，不是通用显卡要求。
忠实修订时保持渲染器、后端／参数、字体、颜色处理和编码条件；引擎变更应作为独立实验核对。

## 4. 声音从分镜阶段参与

原版在 Chrome 的 Web Audio 中离线合成配乐，导出 WAV，再通过 FFmpeg 做母带和 AAC／MP4 输出。
音乐有全片的铺垫、渐强、关键揭示、抽薄、重新推进和收束；音效对应物件事件，不是任意增加的装饰。

本例 120 BPM，一拍 0.5 秒、一小节 2 秒。统一事件协调 2.5 秒计时停止、26 秒拆解、44 秒总数揭示、80 秒“20”的高潮和 152 秒的最终和弦。
同一动作表同时驱动真实转层与咔哒音。并非每次转动都必须踩拍，而是关键揭示有明确重音。

增益包络要明确，避免意外爆音或自动补偿增益。母带后复测实际编码音轨，本项目目标约 −14 LUFS、真峰值不高于 −1.5 dBTP。
响度、波形和偏移量只能证明技术属性，不能证明好听。若当前审查工具无法听音，应说明边界并交由能够听审的人实际试听。

无旁白、120 BPM 和最后九秒收束均为本片选择，不是以后所有旁白片或其他节奏影片的固定参数。

## 5. 检查真正交付的成片

分幕看图，对关键动作看连续帧，依据画面修正；编码后再检查最终 MP4。分别记录：

| 检查 | 证据 | 单凭它不能证明什么 |
|---|---|---|
| 事实与机制 | 来源、单位、真实状态和目标验证 | 观众已经理解或画面已经好看 |
| 排版与动效 | 关键帧、选定连续帧拼图 | 全片连贯观感或完播率 |
| 媒体完整性 | 帧数、时长、完整解码、编码和音频指标 | 剪辑吸引力或配乐悦耳程度 |
| 实际体验 | 连续看片、真实听审、目标尺寸／设备 | 没有观众数据时的传播效果 |
| 交付 | 正确成片、保留原件、校验和一致 | 云端上传或其他设备同步已完成 |

主文字避让主体和平台遮挡区。标签要检查未完成、进行中、全部完成三种状态；勾号会改变宽度。
标注与物件使用同一身份和当前变换，不依赖记忆中的初始坐标。自称审片不够，还要有实际看过的图和相应修改记录。

成片复制到用户约定的位置，保留工程与原版，核对交付副本。本项目用户选择的是 iCloud 云盘的下载目录，应解析实际文件夹，不能默认普通系统 Downloads。
文档不公开个人本机路径，也不把本地文件存在等同于 Apple 服务端／其他设备已经同步。

## 6. 本次修订比较留下的经验

一次 Codex 修订把画面导出换成原生 Canvas，把 Web Audio 换成另一实现，并加入计时黑底、红色标注图形、收窄的机位和更多停顿。
它修复了真实的标注问题，但用户更认可原片的整体呈现。技术正确不足以把整组审美变化称为优化；引擎变化增加了变量，也未证明能解释每一处观感差异。

随后忠实修订回到原版源码与制作链路，仅改两个场景文件，修锁标、F2L 编号和标签间距。
原时间轴、机位、字体、核心绘制、配乐和 Chrome 导出器保留。核对结果：

- 158 秒，1080×1920，30 fps，共 4740 帧；
- 43 个原分块、3840 帧的编码数据与时间戳相同；
- 10 个相关分块、900 帧由原 Chrome 导出器重渲；
- 全部 7408 个原 AAC 编码包及时间戳相同，没有重新编码声音；
- 完整解码通过，最终音轨 −14.3 LUFS、−1.98 dBTP。

这些结果证明相应的保留情况和技术属性，不代替连续看片、主观听审或实体手机测试；本次审查没有声称完成后三项。

后续修订从已选原片出发，用最小改动修正确定问题，先对比受影响的短片段；审美重做和渲染引擎替换单列验证。

## 7. 可复用的工作指令

> 以已经认可的样片为审美和制作参考。先准备事实、分镜和风格测试。每个镜头安排一个主要解释动作，画面、文字、音乐和音效共用命名时间点。
> 保持已选渲染器、字体、镜头语言和声音方式，分幕审看，并检查最终编码。
> 修改已有影片时只修确定问题，不混入无关界面元素、全片停顿或未说明的渲染／音频引擎替换。
> 提前安排结尾回扣和声音尾部，保留原版，记录实际验证范围，交付到约定目录。已有明确授权的步骤不重复询问同一决定。
